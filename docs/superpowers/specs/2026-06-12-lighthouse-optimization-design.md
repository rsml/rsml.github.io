# Lighthouse Optimization Fixes

**Date:** 2026-06-12
**Scope:** Three targeted fixes surfaced by a full Lighthouse audit of rsml.github.io

## Context

Lighthouse 13 audit results against the live site (rossmiller.dev):
- Accessibility / Best Practices / SEO: all 100
- Performance: null (LCP errors out, driving the score to null)
- All measured perf metrics are excellent: FCP 0.8s, TBT 0ms, CLS 0, Speed Index 0.9s, TTI 0.8s

Three real issues identified:

1. `bookshelf-loading.webp` (953 KB) loads as the strip thumbnail because the optimize script intentionally skips GIF-type assets (to preserve animation). No `-thumb.webp` sidecar exists.
2. All `<img>` tags in WorkRow.astro lack `width`/`height` HTML attributes. The browser cannot reserve space before images load, and Lighthouse 13 errors on LCP when no sized element is present.
3. Cloudflare cache TTL is 10 minutes (GitHub Pages default, `max-age=600`). The intended 3-day TTL is not being applied. Cache-insight estimates 2,721 KiB of savings if assets cache properly.

## Fix 1: bookshelf-loading thumbnail

**Change:** In `src/data/work.yaml`, change the `bookshelf-loading.webp` asset from `type: gif` to `type: image`. No other YAML changes.

**Why it works:** `stripImageRef()` in the optimize script returns null for `gif` assets (to preserve animation) and returns `asset.src` for `image` assets. Changing the type means `pnpm optimize` picks it up in `thumbJobs` and generates `bookshelf-loading-thumb.webp` as a static first-frame WebP at 600px tall (2x shotHeight of 300), quality 80. The optimize script's `sharp` call does not pass `{animated: true}`, so it naturally extracts the first frame.

**Lightbox behavior:** Unchanged. The lightbox renders `image` type as `<img>`, and the original animated WebP will still autoplay in the lightbox.

**Expected savings:** ~850 KB per page load (953 KB -> ~100 KB for the thumb).

## Fix 2: width/height attributes on strip images

**Change:** In `WorkRow.astro`, import `sharp` at build time and read pixel dimensions for each strip src. Emit `width` and `height` on every `<img>`.

**Approach:** In the Astro component frontmatter (build-time only):
1. For each asset, resolve its strip src via `resolveStripSrc(asset)`.
2. If the src is a local absolute path (starts with `/`), read its dimensions from `public/` using `sharp(absPath).metadata()`.
3. If the src is an external URL (YouTube thumbnail), use hardcoded 320x180.
4. Pass `width` and `height` to the `<img>` tag. CSS (`height: var(--shot-h); width: auto`) still controls the display size; the HTML attributes only inform the browser of the intrinsic aspect ratio for layout reservation.

**Build-time cost:** ~70 `sharp.metadata()` header reads add roughly 100-200ms to the build. Acceptable for an SSG deploy-time build.

**Effect:** Browser reserves correct space before images load (prevents CLS). Lighthouse can identify the LCP element (the first strip image in the first work row, already `loading="eager"` and `fetchpriority="high"`).

## Fix 3: Cloudflare cache TTL

**Change:** Add two Cache Rules in the Cloudflare dashboard for the `rossmiller.dev` zone.

Cannot be done via MCP (read scope only). Implementation is manual dashboard steps provided as instructions.

**Rule 1** (content-hashed Astro assets, safe to cache permanently):
- URL match: `rossmiller.dev/_astro/*`
- Cache Level: Standard
- Browser Cache TTL: 1 year

**Rule 2** (general portfolio assets):
- URL match: `rossmiller.dev/*`
- Cache Level: Standard
- Browser Cache TTL: 7 days

**Note:** Astro hashes all `_astro/` filenames at build time (e.g., `index.DY6eZFce.css`), so 1-year TTL is safe. New deploys produce new hashes, so stale-content risk is zero for `_astro/*`.

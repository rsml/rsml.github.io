There’s always been a desire to have very strict guardrails on code (conventions, type safety, strong linting, perfect code coverage, etc) in order to prevent certain classes of bugs. However for many teams, these desires have come in tension with the practicalities of running a software team. For instance, every new guardrail could historically make it slower to onboard a new engineer, increase developer frustration, and slow a team’s velocity.

Before AI coding agents, we optimized for the ability to write and maintain code in a fast and high quality way. Now that code is cheap, we need to shift focus specifically to the speed at which humans can validate code in a fast and high quality way.

One of the best ways to increase confidence in your code is by using a strict type system. While the following patterns add additional verbosity which makes code slightly slower to read, they are such powerful guardrails that I believe they are almost always worth adopting in AI-generated code.

Here's a quick survey of some of the advanced patterns you can do in TypeScript to make your code safer. For a more detailed explanation of each pattern, click or tap on the corresponding section header below.

### [Branded types](https://www.learningtypeScript.com/articles/branded-types)

```ts
// bad
declare function getUser(id: string): User;
const orderId = "ord_123";

// compiles fine, even though orderId is an order id, not a user id
getUser(orderId);
```

```ts
// good
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
declare function getUser(id: UserId): User;
const orderId = "ord_123" as OrderId;

// Error: OrderId is not assignable to UserId
getUser(orderId);
```

All types are stripped out at runtime. So at runtime UserId and OrderId are still plain strings.

### [Phantom types](https://dev.to/busypeoples/notes-on-typeScript-phantom-types-kg9)

Strictly speaking, Phantom Types are a superset of Branded Types. The difference is, Phantom Types use a parameterized type instead of a constant type. For instance instead of the "__brand" being the constant "UserId", a phantom type would be "__brand" of a variable type, e.g. "T".

So let's rewrite the UserId and OrderId branded types from the previous example using a phantom type called `Brand<T, U>`.

```ts
// This is the Phantom Type since it is parameterized
type Brand<T, U extends string> = T & { readonly __brand: U };

// These are Branded Types
type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

// Error: OrderId is not assignable to UserId
getUser(orderId);
```

### [Wrapper types for taint tracking](https://dev.to/busypeoples/notes-on-typeScript-phantom-types-kg9)

```ts
// bad
const apiKey: string = user.apiKey;

// Dangerous! This compiles, and a secret will leak in the logs
log(apiKey);
```

```ts
// good

// Sensitive<T> is a phantom type
type Sensitive<T> = { readonly __sensitive: T };

function protect<T>(value: T): Sensitive<T> {
  return value as Sensitive<T>
}

function reveal<T>(value: Sensitive<T>): T {
  return value.__sensitive;
}

// apiKey is now protected
const apiKey: Sensitive<string> = protect(user.apiKey);

// Error: Sensitive<string> is not assignable to string
log(apiKey);

// Succeeds. Every "reveal" call is greppable, so it is easy to audit.
log(reveal(apiKey));
```

### [Discriminated union](https://www.typeScriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions)

```ts
// bad
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;

    // If we later add { kind: "triange" } this will return 0
    // But it would be better if it returned a compilation error
    default: return 0;
  }
}
```

```ts
// good
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  // added later
  | { kind: "triangle"; base: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default:
      // Error: 'triangle' is not assignable to 'never'
      const __exhaustive: never = shape;
      return __exhaustive;
  }
}
```

The default case is pinned to `never`. So if you forget to handle a case, TypeScript will fail to compile.

### [Typestate](https://catchts.com/type-state)

```ts
// bad
conn.close();

// compiles, but throws at runtime: the connection is closed
conn.send("data");
```

```ts
// good
declare class Connection<S extends "open" | "closed"> {
  send(this: Connection<"open">, data: string): void;
  close(this: Connection<"open">): Connection<"closed">;
}

// conn is Connection<"open">
const closed = conn.close();

// Error: 'send' is not callable on Connection<"closed">
closed.send("data");
```

### [Template-literal types](https://www.typeScriptlang.org/docs/handbook/2/template-literal-types.html)

```ts
// bad
declare function navigate(route: string): void;

// compiles: a typo'd route is just a string, then 404s at runtime
navigate("/usrs/42");
```

```ts
// good
type Entity = 'users' | 'posts'
type Route = `/${Entity}/${number}`
declare function navigate(route: Route): void;

// Error: '/usrs/42' is not assignable to Route
navigate("/usrs/42");
```

Just like in JavaScript, you can use template literals in TypeScript's type system.

A slot like `${number}` matches any string with a number in that position just like `${Entity}` matches any entity in that position. So `/users/42` is a valid `Route`, but `/usrs/42` is not.

### [Smart constructor](https://dev.to/gcanti/functional-design-smart-constructors-14nb)

```ts
// bad
declare function repeat(times: number): void;

// compiles: any number is allowed, whole or fractional
repeat(3.5);
```

```ts
// good
type Integer = number & { readonly __brand: "Integer" };

// toInteger is the smart constructor
function toInteger(n: number): Integer | undefined {
  return Number.isInteger(n) ? (n as Integer) : undefined;
}

declare function repeat(times: Integer): void;

// Error: number is not assignable to Integer
repeat(3.5);
```

Despite `toInteger(n: number)` being a regular function, when it's the only way for the user to get an `Integer` type, it is often confusingly called a smart constructor.

You'd typically run this check once, at the endge of your system. For instance, let's say you have an API route handler with some Zod validation. After a field parses as a `z.int()`, you can then use `toInteger(n: number)` to specity that value's type as an Integer. Now throughout your code you can use the Integer type and have 100% confidence that it is an integer without any additional runtime checking needed.

### [Effect: errors and dependencies](https://effect.website/)

[Effect](https://effect.website/) is a very useful library for AI-generated code because it enforces that errors and dependencies become part of a function's type.

Let's say you have the following Effect code

```ts
import { Effect, Context, Data } from "effect"

type Receipt = { id: string }

class CardDeclinedError extends Data.TaggedError("CardDeclinedError")<{
  reason: string
}> {}

class PaymentGateway extends Context.Tag("PaymentGateway")
  PaymentGateway,
  { charge: (id: string) => Effect.Effect<Receipt, CardDeclinedError> }
>() {}

// The ledger lives in the type:
// succeeds with Receipt, can fail with CardDeclinedError, owes PaymentGateway.
declare function charge(
  id: string
): Effect.Effect<Receipt, CardDeclinedError, PaymentGateway>
```

```ts
// Bad: Does NOT compile.
// Type 'PaymentGateway' is not assignable to type 'never'.
// (CardDeclinedError is fine here. It would just reject at runtime.)
Effect.runPromise(charge(id))
```

```ts
// Good: This is how you handle errors and pass in dependencies
// In this example paymentGateway is the only dependency that needs to be injected

const paymentGateway = {
  charge: (id: string) =>
    Math.random() > 0.5
      ? Effect.succeed({ id: `receipt_${id}` })
      : Effect.fail(new CardDeclinedError({ reason: "insufficient funds" })),
}

const settled = charge(id).pipe(
  // Handle the expected error.
  Effect.catchTag("CardDeclinedError", (e) =>
    Effect.succeed(`Declined: ${e.reason}`)
  ),
  // Provide the needed dependency
  Effect.provideService(PaymentGateway, paymentGateway)
)
// settled: Effect<Receipt | string, never, never>  ->  runnable
const result = await Effect.runPromise(settled)
```

Here the signature says `charge` can fail with `CardDeclinedError` and needs a `PaymentGateway` dependency injected. Due to Effect's strict type system, the TypeScript compiler will not let you run it until you have handled the error and provided the required dependency.

### [Beyond TypeScript](https://en.wikipedia.org/wiki/Refinement_type)

```ts
// not expressible in TypeScript
function at<T>(arr: T[], i: number): T {
  // i could be out of range, and no TypeScript type can promise it is not
  return arr[i];
}
```

There are some things that no TypeScript type can promise. For instance, the function above wants to guarantee that `i` is a valid index. But whether it is depends on a value that only exists once the program runs, and TypeScript's types are gone by then.

Similarly it's impossible to have types that represent "this list is sorted" or "this file handle is used exactly once." Checks like these have to survive into runtime, so they belong to languages built for it ([Rust](https://rust-lang.org/), [Idris](https://idris-lang.org/), [Dafny](https://dafny.org/)) or to a model checker like [TLA+](https://lamport.azurewebsites.net/tla/tla.html).

Despite these limitations with TypeScript's, there above patterns give you a lot of type safetype. The rule of thumb is check a value once, brand it as checked, and trust runtime for the rest.

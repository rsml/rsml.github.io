Due to AI, the bottleneck in shipping great software has shifted from how fast can you write code to how fast can you validate code.

There's always been a desire to have very strict guardrails on code (conventions, type safety, strong linting, perfect code coverage, etc) in order to prevent certain classes of bugs. However these desires could at times come at odds with the practicalities of running a software team. For instance, every new guardrail can potentially make it slower to onboard a new engineer, increase developer frustration, and slow a team's velocity.

Since code is now written by AI, often human time and descernment is a bottleneck. We used to be optimizing for ability write and maintain code in a fast and high quality way. Now we need to shift focus to speed at which a human can validate PRs in a fast and high quality way.

I propose a framework of thinking about these guardrails in three levels of increasing safety. Moving up the levels is not strictly better, because there are tradeoffs which I'll cover in detail. For each class of errors it is up to each team at what level of guardrails they want to be at.


## Level 1: caught when it runs

[Rice's theorem](https://en.wikipedia.org/wiki/Rice's_theorem) states "Rice's theorem states that all non-trivial semantic properties of programs are undecidable" (Wikipedia). What follows from Rice's theorem is it is impossible to write an algorithm that is perfectly decides in a finite amount of time if an arbitary codebase is free of bugs.

At the bottom, nothing static sees the bug. You find out by running the code.

The smallest instrument is a test. It catches bugs about what the code does, something the next two levels can't answer.

```ts
// The test pins the expected behavior. No type system can verify it.
test("10% discount on a $100 order leaves $90", () => {
  expect(applyDiscount({ subtotal: 100, discountPct: 10 })).toBe(90);
});
```

If `applyDiscount` has an off-by-one or the wrong formula, the test fails. The function has the right type, takes the right arguments, and returns a number. The number is just wrong. Only running it against a known answer catches that.

Tests are one instrument at this level. The same level holds everything else you learn by running the code: integration and contract and end-to-end tests for behavior, property-based and mutation testing for the cases a hand-written example would miss, load and chaos tests for resilience, and once it ships, canary releases, feature-flag rollouts, and the whole observability layer of metrics, traces, and alerts. Runtime assertions belong here too, the invariants the types cannot express, like a set of line items summing to the order total. Every one of these runs the code. That is what puts them at the same level.

Some bugs never leave it. Whether a generated report is accurate, whether the feature does what was asked, whether the refund logic matches what finance intended: these are about meaning, and there is no pattern in the source that separates the correct version from a plausible wrong one. This is also where the bugs you never imagined live, the ones no checker covers because nobody thought to write the check. You narrow this level with more tests and better review. You do not empty it.

## Level 2: caught before it runs

The bugs that can leave level 1 are the recurring ones you can describe as a shape. You keep seeing the same mistake in review, and the mistake is something a checker could match in the text. Write the pattern down once and stop reviewing for it.

Here are two such bugs. One belongs at level 3. The other is already home.

The first is logging sensitive user data. The model keeps passing user fields to the logger, and a lint rule flags it. It catches the obvious calls, but it has a hole, and the hole is invisible, because the rule reports green on every leaking line:

```ts
// The linter watches for log(user.<field>). Both of these slip past it.
const value = user.apiKey;  // an assignment, not a log call. the rule says nothing.
log(value);                 // value is a plain string now. silence.

const summarize = (s: string) => log(s);
summarize(user.creditCard); // the log lives in summarize. the call site passes a string.
```

The rule matches the shape `log(user.<field>)`. Rename the value, alias it, or route it through a helper, and the shape is gone but the leak is not.

The second bug is the model reaching for the clock directly.

```ts
// Non-deterministic. Any test that depends on time will be flaky or wrong.
const now = Date.now();
```

You want time to come from an injected clock so tests can control it. A rule bans the global.

```jsonc
// eslint
{
  "rules": {
    "no-restricted-globals": [
      "error",
      { "name": "Date", "message": "Inject a Clock. Direct Date calls are non-deterministic." }
    ]
  }
}
```

This rule has no hole. The bug is the presence of a `Date` call, not a value that travels, so there is nothing to rename or alias your way around. The rule sees every occurrence because every occurrence is the literal token `Date`. You could make `Date` a type error by stripping it from the global types, but that fights the language and catches nothing new. It stays at level 2.

That is the distinction. The sensitive data bug is a value that moves through the program, and a scanner can only watch the spots it was told to watch. The clock bug is a forbidden token that does not move, and a scanner catches all of it. The first wants the type system. The second does not.

## Level 3: the bug cannot be written

Take the sensitive data bug the scanner could not fully contain, and move it where renaming and aliasing cannot reach: into the type of the value itself.

A phantom type carries a tag that exists only at compile time and disappears at runtime.

```ts
declare const sensitive: unique symbol;

// Type-only tag. At runtime the value is unchanged.
type Sensitive<A> = { readonly [sensitive]: A };

// Mark a value sensitive. Compiles to a no-op; nothing happens at runtime.
const protect = <A>(value: A): Sensitive<A> => value as unknown as Sensitive<A>;

// The only way back to the raw value. One grep finds every exposure.
const reveal = <A>(value: Sensitive<A>): A => value as unknown as A;
```

Now the data layer wraps secrets with `protect` and hands you `Sensitive<string>` instead of `string`, and the same two lines that leaked past the linter stop compiling.

Here is what "cannot be written" means. `log` is typed to take a `string`. A sensitive value has type `Sensitive<string>`, which is an object with a hidden tag, and an object is not a string, so `log(v)` does not typecheck. The only function that produces a plain string from a `Sensitive<string>` is `reveal`. So there is no path through the types that passes sensitive data to `log`. The bad program is not rejected by a rule. It cannot be expressed.

The holes from level 2 are gone, because the type rides on the value. Alias it and the alias is still `Sensitive<string>`. Pass it to a helper and the helper's parameter has to be `Sensitive<string>`, which means the helper cannot reach `log` either. A scanner matches a shape in one place. A type follows the value into every place it goes.

That difference has a name. A linter is unsound: it misses real cases, and the misses are the holes. A type is sound for the property it encodes, so there are no holes to slip through, as long as nobody casts around it. That is the whole jump from level 2 to level 3, and it is why the escape has to collapse to a single audited `reveal`.

The only escape is `reveal`. The sprawling rule (never log sensitive data anywhere) collapses to a single audit point: every call to `reveal`.

The same climb works for two bugs you normally catch late: the errors a function can produce, and the dependencies it needs. Both are invisible to the lower levels, and both can be lifted into the type.

Errors first. When `charge` can fail and the caller forgets, you find out when the code runs: a rejected promise, a 500, a customer charged twice. The scanner does a little better, but not much. A lint rule can flag an empty `catch`, but it cannot know that `charge` fails with `CardDeclined`, because lint does not track what a function fails with. So put the failures in the type.

Define the failures as tagged errors, and handling every case empties the error channel to `never`.

```ts
import { Effect, Data } from "effect";

// Each failure mode is a distinct type. No stringly-typed error codes.
class CardDeclined extends Data.TaggedError("CardDeclined")<{ reason: string }> {}
class UserNotFound extends Data.TaggedError("UserNotFound")<{ id: string }> {}

const handled = charge("123").pipe(
  Effect.catchTags({
    CardDeclined: (e) => Effect.succeed(declinedReceipt(e.reason)),
    UserNotFound: (e) => Effect.succeed(missingReceipt(e.id)),
  }),
);
//    ^? Effect.Effect<Receipt, never>
// never means: every failure has been handled. the compiler verified it.
```

The exhaustiveness is the point. Add a `FraudHold` failure to `charge` later and its type gains `| FraudHold`. The handler above no longer covers every case, so `handled` becomes `Effect<Receipt, FraudHold>` instead of `never`, and any boundary you have typed to demand a fully handled error channel stops compiling until someone deals with it. A new failure mode cannot enter the system without forcing every handler that claimed exhaustiveness to account for it.

Dependencies make the same climb. Forget to wire one up and, left alone, you find out when the code runs: a crash at startup if you are lucky, a null deref deep in a request if you are not. A scanner cannot tell which services a function needs, so it misses the gap too. Put the requirement in the type, and an effect that needs a service carries that need in its signature.

```ts
import { Context, Effect } from "effect";

// The service interface is declared here. The implementation is injected at the edge.
class Database extends Context.Tag("Database")<
  Database,
  { readonly findUser: (id: string) => Effect.Effect<User> }
>() {}

const getUser = (id: string) =>
  Effect.gen(function* () {
    const db = yield* Database;
    return yield* db.findUser(id);
  });
//    ^? Effect.Effect<User, never, Database>   (Database still required, not yet provided)

Effect.runPromise(getUser("123"));
// type error: Database is still required and has not been provided

const runnable = getUser("123").pipe(Effect.provide(DatabaseLive));
//    ^? Effect.Effect<User, never, never>   // requirement satisfied, safe to run
```

Now the missing dependency is a type error at the line where you run the effect, caught with everything else, instead of a surprise in production.

The three levels are easier to read as a decision than as a ladder. A bug is not always better off higher up; it belongs wherever its kind of mistake is caught, and some kinds have no higher home to climb to.

## When the climb is worth it

Not every bug belongs at level 3. The clock rule already showed one that does not. The cost of level 3 is not false rejections. A model just regenerates when it hits one. The cost is that some constraints are ugly in the type system, and a contraption nobody can read is worse than the bug it prevents. A clean rule with a good message beats a baroque type.

The move makes sense when one of these is true. The dangerous thing is a value that travels, like an API key or untrusted user input, where a scanner leaks and a type does not. Or you need a guarantee you can defend, where "the type system forbids it" is a sentence you can say to an auditor and "we have a rule and we think it is complete" is not. Otherwise, if the rule has no real holes and the type would be line noise, leave the bug at level 2.

## Shaping, not grading

Types have one more advantage over rules, and it exists only because a model is writing the code. A type is in-band: the model sees the constraint while it writes, not after. The signature for `log` says it takes a `string`, so the model sees immediately that `Sensitive<string>` will not work and tends not to write the violation at all. A lint rule is out-of-band, a separate config the model usually does not have in front of it, so it writes the bug, the build fails, and you spend a regeneration. Either way the bug does not ship. But in-band prevents the mistake. Out-of-band only catches it. The difference is whether you are shaping what the model writes or grading it afterward.

## Which concerns can climb

Not every concern can reach every level. Some can be defended at compile time, at the scanner, and at runtime all at once, and those are the ones worth promoting. Others have nowhere higher to go.

<TierMatrix />

Sensitive data tagging has a phantom type at compile time, a lint rule at the scanner, and assertions at runtime. Resilience and security make the same climb: a typed error channel or a branded `SafeHtml` at compile time, a lint rule at the scanner, chaos tests and pentests at runtime. Accessibility stops one step short. It has strong scanners and runtime audits, but types cannot express most of what it requires. Performance is the same: types do not bound runtime cost, so it never reaches compile time. Correctness of meaning has exactly one home, runtime, because there is no static check for whether the output is right.

One caveat about the whole picture. Everything above is one family of defense: catch a violation by inspecting the code. There are others this framework leaves out. You can prevent a bug by construction, which is what level 3 quietly does, by making the bad state unrepresentable so a sound checker holds you to it. You can catch it with human or AI review, which is most of the discretion at level 1. And you can contain it at runtime, with sandboxing, memory safety, or letting a process crash and restart. The levels here are the part you can automate against the source, not the whole of safety.

## The spec gets tighter

Run an AI codebase for a while and you build a feel for which mistakes the model keeps making, which ones are expensive when they ship, and which ones your current checks quietly miss. Those are the ones you promote. The recurring runtime bug becomes a test you keep, then a rule once you can name its shape, then a type once the rule starts leaking. Each step takes something a human had to watch for and turns it into something the model cannot slip past, or cannot write at all.

You are not dragging everything to level 3. You are moving the bugs that earn it and leaving the rest where the cost makes sense. Over time the rules the model writes against get tighter, and the best constraints are the ones that never fire, because the model has stopped making the mistakes they guard against.
